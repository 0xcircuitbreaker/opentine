# 0.40 CDC bake-off: BLOB_PREFIX_DELTA vs FastCDC vs both

**Decision (provisional): ship BLOB_PREFIX_DELTA in its "middle-out" form
(`bpd-middle`, pack v3 encoding 3, `opentine/repository/_blob_delta.py`).
FastCDC is not shipped; it stays in the bench script only, to be re-run once a
consented real corpus exists.**

## The corpus caveat

ROADMAP §4 asks for the bake-off on the real transcript corpus plus at least 50
real Claude Code and Codex sessions collected with consent. **No consented
real-user corpus is available.** The only real session data in the repository
are the 14 harness fixtures under `tests/fixtures/harness/**/*.jsonl` (95
lines, 76.5 KB in total: Claude Code stream, Codex exec, and 12 other
dialects). That is too small to separate the options, because every one of
them fits in a single zstd window. The decision below therefore rests on the
synthetic corpus and is **provisional**. It must be re-run with
`scripts/bench/cdc_bakeoff.py` once a consented corpus exists.

## Method

To reproduce: `uv run python scripts/bench/cdc_bakeoff.py --runs 40`. Use seed
37, 24 steps per run, zstd-19 and 16 MiB blocks. Linux, Python 3.13 and
backports.zstd. The runner was shared with other jobs, so treat the times as
indicative.

The script uses three corpora. Objects are in v3 pack order.

| Corpus | Objects | Logical bytes | What it is |
|---|---|---|---|
| synthetic | 3,479 | 150.7 MB | `scripts/bench/corpus.py` runs through `Repo.put_run`, plus the growth blobs below |
| growth | 1,000 | 135.9 MB | each synthetic run's transcript saved after every step (the `put_transcript` pattern) |
| fixtures | 95 | 76.5 KB | every real fixture transcript, saved after every line |

Every option lays objects out as a v3 local pack does: one kind per block, with
each block compressed by zstd. The script measures three things:

* **size:** blocks plus anything stored outside them. CDC recipes cost 36 bytes per chunk reference, and patch-from frames cost 32 bytes of base id each.
* **CPU:** process time to build the stored form.
* **random-access latency:** p50 and p95 over 200 seeded blob reads. Each read starts cold, so every block it touches is inflated afresh.

These are the options:

* `full`: v3 as shipped in 0.37-0.39.
* `bpd-middle`: the base is the blob with the longest shared prefix plus suffix among the 16 blobs before it, and only the differing middle is stored. The block codec compresses that middle.
* `bpd-patchfrom`: the same bases, with zstd-19 `--patch-from` (the base body as a raw prefix dictionary). Each frame is stored on its own.
* `cdc-2k`, `cdc-8k`, `cdc-64k`: normalized FastCDC. Unique chunks go in the blocks.
* `bpd+cdc-8k`: the `bpd-middle` stored forms, chunked and deduplicated.

A second run without the growth blobs used 160 runs, 9,908 objects and about

* v3: 2,030,362 bytes, about 29x, gc 22.3 s.
* delta: 1,885,984 bytes, about 31x, gc 15.1 s.

At 40 runs (14.8 MB, everything in one zstd-19 window) the two are equal:
502 KB against 505 KB.

### Autopack latency gate (§4)

**The gate:** autopack may write delta packs only if its p95 latency is at most
1.5x the same autopack without them. The 0.36 autopack is the v3 path without
deltas. The script measured one autopack-sized pack every 4 runs, which is
about the 256-object threshold, over 40 runs (10 calls).

| | p50 s | p95 s |
|---|---|---|
| without deltas | 0.425 | 1.983 |
| with deltas | 0.456 | 1.815 |

The p95 ratio is **0.92, so the gate passes**. Once a repository opts in,
autopack writes blob deltas too.

## Decision and reasoning

1. **Transcript growth is the target workload of 0.40, and `bpd-middle` wins it clearly.** On that workload it reaches 497x. The next best are bpd+cdc (423x) and cdc-8k (270x). It also has the lowest encode CPU of any transform.
2. **CDC-8k wins the synthetic mix** (151x against 81x). Its gains come from the corpus's 256 KiB blobs that change by one line between runs. However:
   * it costs 2.8x the CPU (pure-Python chunker; a C chunker would narrow this);
   * its p95 random-access latency is 1.8x worse;
   * it needs a new recipe/chunk object model that transfer would have to understand.

   The bench saw low CDC dedup on edited files, and the research said CDC pays off only above about 1 MiB (§4). Both remain open questions without real data.
3. **Patch-from loses on size in local packs.** Each frame is compressed alone, outside the block, so the block codec cannot also exploit cross-object repetition. It is also the slowest option. Middle-out leaves the entropy coding to the block.
4. **Combining the two is not better than either one on its own workload.**

So BLOB_PREFIX_DELTA (middle-out) ships. CDC is not cut, because there is no
real data to cut it on. It stays in `scripts/bench/cdc_bakeoff.py` and should
be re-evaluated, especially at 8 KiB, against a consented corpus of at least
50 sessions before 1.0.
