# `tine query` index at one million runs (0.65)

Command: `python scripts/bench/query_index.py --runs 1000000 --real 10000
--out docs/bench/0.65-query.json` on a 4-core x86_64 container, Python 3.13.
Raw numbers: docs/bench/0.65-query.json.

Acceptance targets (plan 0.67): index build under 10 minutes for a
1e6-run repository, a typical aggregate query under 2 s.

## Index write and queries (synthetic, 1e6 runs)

1,000,000 runs, 3,000,000 steps, 100,000 monitor verdicts and 100,000 eval
verdicts written through the same staged write a rebuild uses: **12.0 s**,
a 1.6 GB index.

| Query | Seconds |
| --- | --- |
| cost by model (`costs` view, 3e6 rows, GROUP BY) | 1.02 |
| top 10 costly runs (GROUP BY run, ORDER BY) | 0.56 |
| runs per status | 0.25 |
| eval pass rate | 0.07 |
| monitor actions | 0.03 |

Every typical aggregate is under 2 s.

## Reading objects (real runs, extrapolated)

Writing a million real runs takes far longer than indexing them, so the
bench stores 10,000 real runs (3 steps each) and rebuilds from them:

| Reader | ms per run |
| --- | --- |
| serial | 1.20 |
| 4 worker processes | 0.64 |

Extrapolated full rebuild at 1e6 runs with 4 workers: 0.64 ms x 1e6 + 12 s
= **about 651 s (10.9 min)**, just over the 10-minute target on this
machine. Rebuilds use up to 8 workers, so it scales with cores; on 4 cores
the target is missed by about 9%. Object reading (pack lookup and path
checks in the store) dominates; the SQLite write is under 2% of it.
Queries never wait on a rebuild unless the index is missing or `--refresh`
is given.
