# `tine transcripts` index at 100,000 transcripts (0.74, release 0.73.0)

Command: `python scripts/bench/transcripts_index.py --transcripts 100000
--queries 40 --real 300 --out docs/bench/0.73-transcripts.json` on a 4-core
x86_64 container (Intel Xeon 2.10 GHz, 15 GB RAM), Python 3.13, numpy 2.5.3
installed. Raw numbers: docs/bench/0.73-transcripts.json.

Target (plan 0.74): 100,000 transcripts indexed in under 30 minutes on an
8-core CPU. No 8-core machine was available; the numbers below are from 4
cores.

## Embed and write (synthetic, 100,000 transcripts)

100,000 transcripts from the seeded generator (`tests/transcript_corpus.py`,
8 planted behaviours in 100 runs each), embedded with `transcript-hash/1` in
4 worker processes and written through the staged index write a rebuild
uses: **139.5 s** (1.40 ms per transcript), a 139 MB index.

## Search (exact, 100,000 runs)

| Measure | Value |
| --- | --- |
| load the index | 4.7 s |
| median top-50 query (numpy scan) | 0.41 s |
| seeded-behaviour recall at top 50 (40 queries) | 0.908 |

## Reading objects (real runs, extrapolated)

300 real runs stored with `Repo.put_run` and indexed: **7.1 ms per run**
serially. (300 runs fit in one 1,000-run chunk, so the 4-worker figure,
7.7 ms, ran on one process too.) Embedding (about 5.6 ms of CPU per
transcript in the synthetic run above) is most of it; reading objects is the rest.

Extrapolated full build at 100,000 real runs: serially about 7.1 ms x 1e5 =
**about 12 minutes on one core**, under the 30-minute target before any
parallelism. A build of 5,000 runs or more uses up to 8 worker processes.
