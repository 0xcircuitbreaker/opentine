# 0.49 bench: FastCDC stored form in the object store

To reproduce: `uv run python scripts/bench/fastcdc_store.py --mib 8 32`.
Python 3.13 on a shared 4-core Linux runner, in-memory blob client (no
network), `LocalKeyProvider` sealing, default parameters (min 256 KiB,
average 1 MiB, max 4 MiB; payloads of 8 MiB or more are chunked). The corpus
is synthetic transcript-like JSON lines, seed 49. Treat times as indicative.

| Payload MiB | Chunks | Mean chunk KiB | Chunking MiB/s (CPU) | put s (CPU) | New chunks after a 1% append | New stored bytes after a 1% append | Chunks fetched for a 4 KiB range | 4 KiB range ms | Whole get ms |
|---|---|---|---|---|---|---|---|---|---|
| 8 | 7 | 1170 | 13.9 | 0.82 | 1 | 1.3% | 1 | 12.1 | 56.9 |
| 32 | 25 | 1311 | 10.4 | 3.76 | 2 | 2.3% | 1 | 52.5 | 279.2 |

What the numbers say:

* **Dedup across versions works as intended.** A transcript that grows by 1%
  stores one or two new chunks (1-2% of the bytes) instead of a second full
  copy. That is the case the hosted service sees: a session saved after every
  step.
* **Lazy fetch reads one chunk for a small range** instead of the whole
  object, about 5x faster than a whole `get` at both sizes here; the gap grows
  with object size and with real network latency.
* **Chunking is pure Python and CPU-bound** at about 10-14 MiB/s. That is
  fine for a server that receives a few large payloads, and it only runs on
  payloads of 8 MiB or more. A native gear-hash loop is the obvious follow-up
  if hosted traffic needs more.

Correctness rules the bench does not measure, covered by `tests/test_049_fastcdc.py`:
oids are unchanged (the manifest is a stored form), each fetched chunk is
checked against its SHA-256, and `get` re-hashes the joined envelope against
its oid, so a manifest that names other self-consistent chunks still fails.

Note: the 0.40 bake-off script (`scripts/bench/cdc_bakeoff.py`) builds its
gear table with a fresh `random.Random(40)` per entry, so all 256 entries are
equal and its FastCDC variants did not cut on content. Its `cdc-*` rows should
be re-run with one generator before they are cited again. The 0.49 chunker
(`opentine/remote/_fastcdc.py`) uses one generator and a test pins that the
table has 256 distinct entries.
