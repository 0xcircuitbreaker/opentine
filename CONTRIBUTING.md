# Contributing to OpenTine

Thanks for helping. This page is the whole contributor guide: how to set up, how
to run the tests, and the standing gates a change has to clear.

## Setup

OpenTine develops with [uv](https://docs.astral.sh/uv/) and supports Python 3.11
through 3.14.

```bash
git clone https://github.com/0xcircuitbreaker/opentine.git
cd opentine
uv sync --locked --all-extras
uv run tine --help
```

`--all-extras` installs every provider SDK plus the MCP and LangChain extras, so
the whole suite is importable. No API key is needed: nothing in the default test
selection calls a provider.

## Running the tests

```bash
uv run pytest tests -m "not live and not live_harness"
```

That marker selection is the one CI uses. The `live` tests need provider
credentials and the `live_harness` tests need an agent CLI installed, so both are
opt-in:

```bash
uv run pytest tests -m live --provider anthropic
uv run pytest tests -m live_harness --agent-harness codex
```

## The gate list

Run all of these before opening a pull request. CI runs them on Linux, macOS,
and Windows across Python 3.11–3.14.

```bash
uv run ruff check .
uv run ruff format --check .
uv run python scripts/check_architecture.py
uv run pytest tests -m "not live and not live_harness" -q
uv build --no-build-isolation --sdist --wheel --out-dir dist
uv run python scripts/check_release_inventory.py dist
uv run python -m twine check dist/*
uv run python scripts/wheel_smoke.py
```

With Docker available, `uv run python scripts/ci_docker.py` rehearses the Ubuntu
lane — lint, format check, the same deselected `pytest` run, `uv build`, and the
wheel smoke test — in one container per Python version, defaulting to 3.11, 3.12,
and 3.13. `--python VERSION` is repeatable and replaces that default set. It does
not run the architecture, release-inventory, or `twine` gates, and GitHub Actions
remains authoritative for macOS and Windows.

## The standing rules

These are not style preferences. Each one is enforced by a test or a script, and
each exists because it was violated once.

### 1. 250 physical lines per module

`scripts/check_architecture.py` fails when any file under `opentine/` exceeds 250
physical lines. The same script enforces two more architecture gates:

- **`opentine/kernel.py` may import nothing outside the standard library.** It is
  the trusted semantic kernel — canonical encoding, typed ids, immutable
  envelopes — and its whole value is that it depends on nothing. The gate
  constrains what the kernel depends on, not what depends on the kernel.
- **Layer boundaries.** `billing` may import none of `models`, `remote`,
  `repository`, or `runtime`; `models` may import neither `remote` nor
  `repository`; `repository` and `trace` may import neither `models` nor
  `remote`; `remote` may not import `models`.

Splitting a module is the expected response to the line gate. `docs/`, `tests/`,
and `examples/` are exempt from the line count, but keep example scripts tidy —
they are the first code a newcomer reads.

### 2. A newer OpenTine must read older stored data

From v0.3.0 on, stored data is a compatibility contract. `tests/fixtures/compat/`
holds golden artifacts and repositories produced by the **real published**
release of each version, and `tests/test_backwards_compat.py` proves the current
build still loads them, still verifies their digests and signatures, and still
opens and `fsck`s their repositories.

Fixtures are never regenerated for an old release: their bytes are the evidence.
Each new release adds a sibling `tests/fixtures/compat/vX_Y_Z/`, generated by
that published release with `scripts/gen_compat_fixtures.py`.

If a change makes an older artifact unreadable, the change is wrong — not the
fixture.

### 3. Every new module must be tracked by git

`scripts/check_release_inventory.py` compares the built sdist and wheel against
`git ls-files`. An untracked runtime module passes every local test (it is on
disk) and then ships as a broken, unimportable package. This has happened; the
gate exists because of it.

Run `git status` before you tag anything, and add new files in the same commit
as the code that imports them.

### 4. Lint and format are `ruff`, with no exceptions file

```bash
uv run ruff check .
uv run ruff format --check .
```

Line length is 100. The lint rule set is `E`, `F`, `I`, `W`, `UP`.

### 5. A test that shells a binary must declare and guard it

Any test module that spawns an external program **by name** must appear in
`BINARY_DEPENDENT_TEST_MODULES` in `tests/test_release_audit_round11_misc.py`
and must skip when that program is missing (`shutil.which(...)`, or by
containing the `OSError` the spawn raises). `sys.executable` is exempt — it is
the interpreter already running.

A meta-test walks every test module's AST and fails if the two sets disagree, so
the declaration cannot be forgotten. Prefer in-process `opentine.cli.main(argv)`
over spawning `tine`; that is what nearly every CLI test does. After adding such
a test, re-run the **full** suite, not just the new module.

### 6. Examples must run, or be declared

`tests/test_examples_smoke.py` executes the offline examples in-process every
run. A new file in `examples/` must either run offline with no key (add it to
`WORKDIR_EXAMPLES` or `CWD_EXAMPLES`, depending on how it takes its output
directory) or be declared credential-dependent (add it to
`CREDENTIAL_DEPENDENT_EXAMPLES`, where it is compile-checked only). The test
fails on any undeclared example, so an example cannot rot unnoticed.

### 7. Documentation must match the shipped CLI

A doc that names a flag which does not exist is a bug. Before documenting a
command, confirm it with `tine <verb> --help`. Where this repository's prose and
`--help` disagree, `--help` is authoritative and the prose is the defect.

## Pull requests

- Branch from `main`; do not push directly to it.
- Keep the change and its tests in the same pull request.
- Add a `CHANGELOG.md` entry under the version in development when behaviour
  changes; the top heading is the newest release.
- Explain *why* in the commit body. The "what" is in the diff.

Report bugs on the [issue tracker](https://github.com/0xcircuitbreaker/opentine/issues).
Report vulnerabilities through [SECURITY.md](SECURITY.md), **not** a public
issue.

## Where things live

| Path | What is in it |
|---|---|
| `opentine/` | The package. `kernel.py` is the trusted core; `cli.py` and `_cli_*.py` are the CLI; `repository/`, `trace/`, `models/`, `billing/`, `remote/`, `harnesses/`, `integrations/` are the layers. |
| `tests/` | The suite, including the compat fixtures and the meta-tests described above. |
| `examples/` | Runnable scripts; four of them run offline. |
| `docs/` | [CONCEPTS.md](docs/CONCEPTS.md), [GETTING_STARTED.md](docs/GETTING_STARTED.md), [CAPTURE.md](docs/CAPTURE.md), [API.md](docs/API.md), [REPOSITORY.md](docs/REPOSITORY.md), [TINE_FORMAT.md](docs/TINE_FORMAT.md), [PRICING.md](docs/PRICING.md), [SECURITY_MODEL.md](docs/SECURITY_MODEL.md), [RELEASING.md](docs/RELEASING.md), [TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md). |
| `scripts/` | The gates: `check_architecture.py`, `check_release_inventory.py`, `wheel_smoke.py`, `ci_docker.py`, `gen_compat_fixtures.py`, `sign_pricing_catalog.py`. |
